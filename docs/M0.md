# M0: Ambient API go/no-go

> The probe code (`wall/m0.py`, `wall/sources/ambient.py`, their tests and `GOOGLE_SETUP.md`) was removed on 2026-11-08, after the Google Cloud project was deleted. This file is the record of what was measured.
State goes in `backend/data/`: `token.json` (mode 600), `m0-state.json`, and `m0-watch.jsonl`.

## Prerequisites (as run at the time; the setup guide and code are gone)

1. Create a Google Cloud project and enable the **Photos Ambient API**.
2. Set the OAuth consent screen to *External → In production* (unverified is fine). If it's in *Testing*, add both Google accounts as test users.
3. Create an OAuth client of type **TVs and Limited Input devices**.
4. Put the client id and secret in `.env` at the repo root (see `.env.example`).
5. Create a **shared** album in account A, turn on collaboration, and join it from account B.

## Run

```sh
cd backend
uv run python -m wall.m0 auth       # open the URL, enter the code, sign in as account A
uv run python -m wall.m0 device     # open settingsUri, pick the SHARED album; waits until it's set
uv run python -m wall.m0 list       # existing items, plus whether two listings match
uv run python -m wall.m0 watch      # then upload a photo from account B; prints "NEW … after Ns"
                                    # while it's running, delete a photo and look for "REMOVED"
uv run python -m wall.m0 download <id-prefix>   # expect image/jpeg, a few hundred KB
uv run python -m wall.m0 reset      # optional: remove the probe device
```

`watch` polls every 20 s for 20 minutes, about 60 API calls, well under the 240/device/day quota.

## What to check

The API reference says `mediaItems.list` is an ambient feed: when `nextPageToken` is missing,
"more content may still exist", and pages may repeat items. The design's `list_all` deletion
detection depends on getting a complete, stable listing, so `list` and `watch` report
`exhausted`, `duplicates`, and whether two listings match.

## Results (run 2026-11-06)

| Check | Pass if | Result |
|---|---|---|
| Unverified app can get a token for `photosambient.mediaitems` | `auth` prints OK | ✅ Pass, after adding account A as a test user (Testing mode) |
| Device is created and `settingsUri` opens | `device` prints the link | ❌ **Fail**: `devices.create` → `PERMISSION_DENIED: You do not have permission to perform the requested operation. Please refer to the partner program at https://developers.google.com/photos/partner-program/overview.` |
| A **shared** album can be picked as a source | `mediaSourcesSet=true`, album listed | ⛔ Not reachable (no device) |
| A photo uploaded from account B is returned | `watch` prints NEW | ⛔ Not reachable |
| Delay from upload to NEW | ≤ 2 min good, ≤ 10 min acceptable | ⛔ Not reachable |
| Listing is complete and stable for one album | `exhausted=True`, `same set=True` | ⛔ Not reachable |
| Deletion is visible | `watch` prints REMOVED within ~5 min | ⛔ Not reachable |
| Download at `w1600-h1600` is JPEG (also for an HEIC upload) | `image/jpeg` | ⛔ Not reachable |

**Decision: NO-GO for Ambient. Build `ShareLinkSource`** (DESIGN.md §10, M0 failure path).

OAuth works for any project, but the Ambient API's device endpoints only work for apps admitted to
the Google Photos partner program. A personal, unverified project for a one-off party can't count on
that approval, so the design's assumption that we can use it "unverified / test mode" doesn't hold.

Follow-ups:
- M1 implements `ShareLinkSource` behind the existing `PhotoSource` interface; nothing downstream
  changes. A share-link prototype should first measure the same things: delay from upload to
  visibility, how deletions show up, the image size and format served, and how many photos one fetch
  returns.
- The Ambient client and probe were later removed (see the note at the top). If partner access is
  ever granted, they'd have to be rewritten from the API reference.
- Revoke the probe's token when convenient: <https://myaccount.google.com/permissions>, then delete
  `backend/data/token.json`.

## Share-link spike (2026-11-06)

This checks that `ShareLinkSource` is a workable replacement. The test used album `shared_test`, owned
by account A, with photos added from account B. A throwaway script polled the album every 20 s.

**How it works**
1. `GET https://photos.app.goo.gl/<id>` with a non-browser User-Agent returns **302** to
   `https://photos.google.com/share/<albumId>?key=<key>`. A browser User-Agent gets a JavaScript landing
   page with no redirect, so always use a non-browser User-Agent for this step.
2. `GET` that URL with a browser User-Agent. The page embeds `AF_initDataCallback({key: 'ds:1', … data: […]})`.
   Parse `data` as JSON. No login or cookies are needed.
3. `data[1]` is the list of items. Each item has:

   | Index | Field |
   |---|---|
   | `[0]` | stable media id (`AF1Qip…`) |
   | `[1][0]` | `lh3.googleusercontent.com/pw/…` base URL |
   | `[1][1]`, `[1][2]` | width, height |
   | `[1][9][0]` | file size in bytes (missing on some items) |
   | `[2]` | taken time (ms since epoch) |
   | `[4]` | timezone offset (ms) |
   | `[5]` | **time added to the album** (ms since epoch) |
   | `[6][0]` | owner (contributor) id |
   | last element (dict) | has key **`"76647426"`** only for **videos**: `[duration_ms, null, w, h, …, [video_url]]`. Skip these items. |

   `data[2]` is the next-page token (`''` means no more pages). `data[3]` holds album metadata: title, contributors, and `data[3][21]` = **total item count**.
4. Download with `<base URL>=w1600-h1600`, which returns `image/jpeg` at about 240 KB with no auth. (`=d` returns the original file.)

**Results**

| Check | Result |
|---|---|
| Photos added by another contributor appear | ✅ 7 photos from account B, each with account B's owner id |
| Delay from upload to visible | ✅ **About 6 s** after Google's "added" time, seen on the very next poll. The 2-minute target is easily met with a 90 s sync. |
| Deletions disappear | ✅ Seen on the next poll after the delete (≤ 20 s) |
| JPEG at 1600 px | ✅ `image/jpeg`, 239 KB |
| Pagination for large albums | ✅ **At 114 items (113 photos + 1 video), everything comes back in one page** and `data[2]` is `''`. The page limit isn't known; past reports put it around 300–500. Defense: compare `len(data[1])` with `data[3][21]` on every fetch and log a loud warning if they differ (and don't mark missing items as removed). Add `batchexecute` paging only if the warning ever fires. |
| Videos | ✅ Detectable: only videos carry the `"76647426"` key (duration, size, video URL). Skip them. It's not yet known whether Live/motion photos also carry it; check with one in the golden set. |

**Decision: GO for `ShareLinkSource`.** It's faster than the Ambient API would have been (seconds instead of
minutes), and deletion detection is reliable because every fetch returns the full listing. The main risk
is that Google can change the page format without notice. Keep the parser small, test it against a saved
copy of the page, and log loudly if `ds:1` stops parsing.
